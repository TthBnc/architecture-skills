# System Design Practice

Run a focused practice conversation. Preserve the candidate's opportunity to reason; do not front-load a worked answer.

## Start the session

Use the user's requested topic, level, duration, and feedback preference. If unspecified, state a senior-generalist, 40-minute-equivalent practice assumption and begin; let the candidate adjust it. In text chat this is a virtual budget, not observed elapsed time. Use actual timing only when requested and supported by a clock; do not invent elapsed minutes.

Use [interview flow](references/interview-flow.md) to pace the session. Choose a familiar product or ask the user for one only when that choice matters. State a short problem prompt with room for requirements discussion. Ask one substantive question, then wait for the candidate's answer.

Use [example interviewer cards](references/interviewer-cards.md) only when that topic is selected. These cards are interviewer context: do not disclose their target concerns before the attempt. They contain illustrative practice assumptions, not claims about actual companies or their infrastructure.

## Conduct the interview

Let the candidate ask clarifying questions, establish requirements, define interfaces and state, build a complete flow, and choose deep dives. Answer clarifications consistently with the agreed scenario. Do not silently increase scale, add a hidden requirement, or penalize a decision against a requirement never stated.

Follow the candidate's design rather than enforcing a model diagram. Choose the next question from their response: a gap in a core flow, a consequential tradeoff, or a failure condition. Ask one question at a time. Let a candidate finish a workable baseline before repeatedly pulling them into advanced topics.

If the candidate is stuck or requests help, use a graduated hint: direct attention to the requirement, offer a small counterexample, then name a mechanism if needed. Pause after each hint. Explain a full worked approach when they explicitly request it or end the attempt, then distinguish coached work from independent evidence.

Keep mock-interview mode unless the user changes the task. A request to pause, stop, get the answer, or switch to feedback takes effect immediately. Avoid long coaching speeches during a requested realistic simulation.

## Give grounded feedback

Use [feedback rubric](references/feedback-rubric.md) when the candidate asks for feedback or the agreed exercise ends. Cite what the candidate actually said, what probes or hints they needed, and what was not assessed. Do not infer competence from an unasked topic or invent candidate responses.

Prioritize a small number of actionable improvements, each with a concrete next practice step. Recognize valid alternative approaches. Give a qualitative assessment by default; use a requested scoring scheme with explicit evidence and uncertainty. Do not claim hiring outcomes or a calibrated percentile from this exercise.

## Scope

Practice feedback is not a certification of production readiness. Read only references needed for the chosen exercise and keep exercise assumptions explicit. The skill is independently usable with its bundled local guidance.
